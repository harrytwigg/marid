# The CLI terminal view

Every engine with a PTY view (claude, codex, grok, hermes, antigravity, and opencode in server mode) has a **CLI** toggle in the chat pane. It shows the engine's own TUI in an xterm.js terminal, streamed over `/ws/pty/:sessionId`. This page describes what you can do in it and where the edges are.

## Two ways to type, and they mean different things

- **The composer** (the message box under the terminal) sends an ordinary Jinn message. It becomes a Jinn turn: queued like any other, recorded in the Jinn transcript, and injected into the same TUI so you see it run there. Nothing about this changed with.
- **The terminal itself** is a real terminal on a desktop (2026-09-26). Click it, and keystrokes, pastes, the mouse wheel and mouse clicks go straight to the TUI, exactly as if it were running in your own terminal. A thin accent outline shows while the terminal has the keyboard. Click the composer to go back.

What you type into the terminal is you driving the TUI, not a Jinn turn. Whether it reaches the Jinn chat depends on the engine (below).

## Devices

- **Desktop (a fine primary pointer: mouse or trackpad):** interactive, as above.
- **Touch devices (a coarse primary pointer: phones, tablets):** unchanged. The terminal stays display-only: you type in the composer, the keybar under it sends Enter/Esc/Tab/arrows, and you swipe to scroll. xterm's input is disabled there on purpose. A focusable terminal swallows iOS swipes and pops the keyboard over the TUI. One addition: swiping over a full-screen TUI that tracks the mouse (opencode) now scrolls it, by sending the swipe as wheel reports. Before, opencode could not be scrolled on a phone at all.

The mode is chosen when the terminal opens; a pointer change mid-session (docking a tablet) takes effect the next time it opens.

## Keys and mouse

| You do | What happens |
|---|---|
| Type, paste, Enter, Esc, Ctrl-C, arrows… | Sent to the TUI. Esc and Ctrl-C mean whatever they mean to that TUI (both interrupt a claude turn). |
| Ctrl/Cmd+C **with a selection** | Copies the selection instead of sending Ctrl-C. Without a selection it is Ctrl-C. |
| Ctrl+Shift+C / Ctrl+Shift+V | Copy / paste, as in Linux terminals. |
| Mouse wheel | claude: scrolls xterm's own scrollback (about 5–6 lines per notch). opencode: scrolls opencode's message view (it runs full-screen and handles the wheel itself). Alt+wheel scrolls faster. |
| Shift+PageUp / Shift+PageDown | Scroll xterm's own scrollback. Plain PageUp/PageDown go to the TUI. |
| Click, drag | claude: selects text. opencode: goes to opencode (its controls, its own drag-to-copy). To select text in a TUI that has the mouse, hold Shift while dragging (Option on macOS). |
| Click a URL | Opens it in a new tab (http and https only). |

## Per engine: what happens to a turn you type in the terminal

- **claude.** Work turns run inside this same TUI, so the gateway and you share one process.
  - A turn you type is copied into the Jinn chat when it finishes (the external-turn sync reads claude's transcript). For a remote employee the transcript is on the other host, so only the assistant's reply is copied, without your prompt.
  - If a composer message (or any gateway turn) arrives **while your typed turn is running**, the gateway waits for your turn to finish before sending it. Claude Code queues a prompt pasted mid-turn, fires its submit hook at once and, at a tool boundary, folds it into the running turn. Sending it anyway would record your turn's answer as the gateway turn's reply, or merge the two. Verified on claude 2.1.283.
    - The wait ends at your turn's Stop. Failing that (you pressed Esc, which fires no Stop, or Claude Code folded two prompts into one turn), it ends once the TUI has been silent for 4 seconds with no request in flight, unless one of claude's safety prompts is open at the bottom of the screen waiting for you. Claude's spinner redraws continuously while it works, so silence means it has stopped.
    - The waiting message is shown as waiting, not running or stalled: the composer says "Waiting for the turn typed in the terminal" with a **Stop** button, and the sidebar row shows "waiting on terminal". It is never pasted behind a turn that may still be running: that would record your turn's answer as its reply. The wait holds only while claude visibly works or a safety prompt is open, and it has no time limit (COO decision): it is only ever entered because you typed a turn, and you can always stop it.
    - Claude Code re-invoking itself when a background task finishes (a `<task-notification>` prompt) is not a turn you typed and never starts a wait, so an unattended session never parks a message on the terminal. Such re-invocations are handled exactly as before this change.
    - The stop button, "send now" on another queued message, or a new message that interrupts end the wait only: your turn in the terminal keeps running. Anything else that stops the session's engine (deleting, resetting or forking the session, switching its engine, restarting the terminal, stopping a workflow attempt, shutting the gateway down) still replaces the PTY, as it always did.
    - A safety prompt on your turn is yours to answer. The gateway only auto-approves prompts raised by its own turn.
  - If you type and submit a prompt **while a gateway turn is running** (including a new chat's first turn, or a `/command`), Claude Code queues it or, at a tool boundary, folds it into that turn. When it runs as its own turn it is copied into chat afterwards and the next gateway turn waits for it. When it was folded in, the gateway turn's reply may answer both, and your prompt's text is not copied into chat.
  - A turn you type after a gateway turn failed (say, on a rate limit) is your turn, not a late recovery of the failed one: it is copied into chat as its own reply.
  - A turn you interrupt with Esc fires no Stop, so it is not copied into chat.
  - **An unsent draft is glued to the next composer message.** If you type into claude's input box and leave it there without pressing Enter, the next composer message is pasted after your text and sent together. Clear the input (or send it) before using the composer. No reliable keystroke clears a multi-line draft wherever the cursor is, so the gateway does not try.
  - **A composer message is never left stranded in a screen that swallowed it (JIN-3).** Some claude screens discard a paste whole. Pressing Esc twice (say, Esc to stop a command, then Esc again) opens the **Rewind** menu: the paste vanishes, and the Enter after it only closes the menu. The ctrl+o transcript view and a ctrl+z suspend eat it too (verified on claude 2.1.283). Before, the message was stored in chat but never reached claude, and the turn sat "running" for 15 minutes. Now, when claude never acknowledges the paste (its submit hook does not fire within the ~20 s of re-sent Enters), the gateway restarts claude on the same conversation (`--resume`) with the message as its prompt, the same way a first turn starts. The terminal redraws and the message runs. It does not do this while claude is visibly working, because a prompt queued behind work is not lost. "Visibly working" means a tool is running or, on a local session, a model request is in flight. A remote session has no request proxy, so there only a running tool counts. On a local session it also checks claude's transcript, and does not restart if the message is already there (its submit hook was lost), because running it again would do the work twice. A remote session's transcript is on the other host, so there the submit hook is the only evidence: if a remote message arrived but its hook was lost in transit, the restart runs it a second time.
  - In a delegated child session, a turn you type wakes the parent session like any other reply the child produces.
- **opencode (server mode).** The terminal is `opencode attach` on the session's own server. A prompt you type runs in the same opencode session, so later Jinn turns see it in their context, but it is not copied into the Jinn chat.
- **codex, grok, hermes, antigravity.** The terminal is a separate TUI process on the same session; Jinn turns run headless beside it. A prompt you type there runs in that TUI and is not copied into the Jinn chat.

## Known limits (claude)

These are documented behaviour, not bugs to be fixed in this change:

1. **A prompt you type while a gateway turn is running can be folded into that turn, so its reply may answer both.** Claude Code does this itself: a prompt submitted mid-turn is queued, and at the next tool boundary it is handed to the model inside the running turn rather than run separately. The gateway turn's reply then covers your prompt too, and your prompt's text does not appear in the Jinn chat. This is the one you are most likely to notice. To avoid it, wait for the gateway turn to finish before typing in the terminal, or send your message through the composer instead.
2. **A turn you type on a remote employee is copied into chat without your prompt.** The claude transcript lives on the other host, so only the assistant's reply reaches the chat.
3. **Chat order can look out of sequence.** A composer message is stored when you send it, so if it waited behind a turn you typed, the chat reads: your composer message, then your typed prompt and its answer, then the gateway's answer.
4. **A turn you interrupt with Esc is not copied into chat**, because Claude Code fires no Stop for it.
5. **Safety-prompt detection is unverified on claude 2.1.283.** While a turn you typed sits on one of claude's safety prompts, the gateway keeps waiting because it recognises the dialog on screen ("Do you want to proceed?" followed by numbered options, with no input box below them). That shape is pinned to a dialog captured on claude 2.1.220; no safe action raises a safety prompt on 2.1.283 (tried by the producer and by QA). What QA could capture on 2.1.283 is the workspace-trust dialog, which uses the same option selector, and there the options are **not numbered** ("❯ No, exit" / "Yes, I trust this folder") and the footer reads "Enter to confirm · Esc to cancel". If the 2.1.283 safety prompt renders the same way, detection misses it. QA also confirmed on 2.1.283 that a gateway-style paste followed by Enter answers an open dialog with its highlighted option. So in that case the gateway would release the wait after 4 seconds, paste the composer message into the dialog and confirm whatever is highlighted. The same parser drives the gateway's auto-approval of its own turns' safety prompts, which would then not fire (a pre-existing dependency). Avoid sending a composer message while a turn you typed is sitting on a safety prompt.
6. **A composer message sent while the terminal shows claude's agents view (←) starts a new background session.** Claude Code takes the paste as "describe a task for a new session" and submits it there, so the submit hook fires and the gateway counts it as delivered. The message is not lost (it is in the agents view), but it runs outside the conversation. Press Esc to go back before using the composer (JIN-3, verified on 2.1.283).

## How it works (for maintainers)

- **Web** (`packages/web/src/components/cli-terminal.tsx`, `lib/terminal-input.ts`): on a fine pointer, xterm is created with stdin enabled and its `onData` goes out as `{type:"input", data}` frames, split below the gateway's frame cap. xterm answers terminal queries (device attributes, cursor position, mode and colour reports) through the same `onData` stream, so every open viewer would otherwise inject those replies into the PTY as if typed: parser handlers swallow the queries, and focus reports are dropped, so the PTY sees exactly what it saw when the terminal was display-only. Pointer-motion reports (opencode tracks every movement) are coalesced to one per frame. On a coarse pointer the terminal is constructed exactly as before.
- **Gateway** (`packages/jinn/src/gateway/pty-ws.ts`): an `input` frame of up to 64 KiB is written to the PTY unchanged through the engine's `writeRaw`. `/ws/pty` was already operator-only, and it already accepted arbitrary text through `stdin`, so no new capability crosses the socket. The keybar's `key` frames and `stdin` are unchanged.
- **Snapshots** (`engines/pty-snapshot.ts`): a (re)connecting terminal is restored from a server-side snapshot. xterm's serializer restores the mouse tracking mode but not the mouse encoding, so the snapshot now re-asserts `?1006`/`?1016` when the program selected it. Without that, a reconnected browser reported the mouse in X10 to a program that asked for SGR.
- **claude** (`engines/claude-interactive.ts`, `gateway/hook-registry.ts`, `gateway/external-turns.ts`): the engine taps every hook and tracks a turn typed in the terminal: a `UserPromptSubmit` no gateway turn owns, or one beyond a gateway turn's own (argv and pasted prompts both fire one; native commands fire none). It closes on Stop/StopFailure, or on 4 s of TUI silence with no upstream request and no live safety prompt on screen (`viewportShowsLiveSafetyPrompt`: a parsed "Do you want to proceed?" dialog with no claude input line after its options; it fails closed, so the footer is not required, and a dialog quoted in the conversation has the input box below it and doesn't count). `run()` waits on it before touching the PTY, with no time limit; `<task-notification>` re-invocations are ignored (`isBackgroundReinvocation`), so only an operator's turn opens a wait. While it waits, `turnProgress()` reports `waitingForTerminalTurn` (serialized on the session, so the sidebar says "waiting on terminal" instead of "stalled") and the gateway emits `session:terminal-wait` at both edges so the composer can show it. `kill()` on a waiting turn ends the wait; only the operator's own interrupts (`USER_STOP_INTERRUPTION_REASON`, `USER_MESSAGE_INTERRUPTION_REASON`) leave the PTY, every other reason releases it as before. A warm-PTY gateway turn also only accepts a Stop after its own live `UserPromptSubmit`, never one replayed from the hook buffer, and hands a Stop it disowns to the external-turn sync, which is allowed to write while that turn is running. A late-recovery listener (armed after a failed turn) stands down at the next `UserPromptSubmit`.
- **Undelivered paste (JIN-3)** (`engines/claude-interactive.ts`): a warm-PTY turn pastes its prompt and confirms the submit by its own `UserPromptSubmit` (`pasteAndSubmit`, 12 CR retries at 1.5 s, paused while `busy()`: a tool in flight or, locally, an upstream request). When the retries run out, `onUnconfirmed` calls `redeliverByRespawn`, which takes the cold path run() uses for a model switch. It skips the respawn if a local transcript already holds the prompt (`transcriptHasPromptSince`, a whitespace/backtick-normalized match scanned from the end). Otherwise it unbinds `boundProc`, releases the PTY, re-registers the turn's hook callback (the lifecycle's `onCleanup` unregisters it), rewrites the settings and MCP files, and spawns with `--resume` and the prompt in argv. `spawn()`/`spawnRemote()` take a `standDown` predicate (`resolver.isSettled`): it is checked after the local proxy starts, passed to `prepareRemote` as `beforeStage`, and checked again after staging. A turn stopped mid-respawn therefore stages, spawns and attaches nothing. Staging rewrites the session's `gateway.json` with a fresh tunnel port, and a stopped respawn that staged anyway would point the next PTY's hook relay at a tunnel nobody opens.
